문제 정의

'블랙 컨슈머', 'after 신청'처럼 한국인 특화 콩글리쉬는 GPT 학습 분포에서 극히 희소해 교정 품질이 불안정합니다. 온디바이스 목표를 설정하자 두 번째 제약이 즉시 발생했습니다: 14GB 모델을 스마트폰 CPU에서 실시간 추론해야 한다는 것. 모델 압축과 지식 분리를 동시에 설계해 해결했습니다. LLM은 문법·문맥 판단만, 콩글리쉬 용례 검색은 전용 벡터 DB가 담당하는 역할 분업입니다.

핵심 구현
1모델 압축: LoRA + 4-bit NF4 양자화 + 멀티링구얼 토큰 Pruning(~10%) 조합으로 14GB→3.0GB(76%), CPU 추론 0.3s
2지식 분리: FAISS(IVF) + SQLite LRU 캐시 하이브리드로 630개 콩글리쉬 패턴 DB를 0.02초 내 검색하는 개인화 메모리
3응답 지연 2.3s→0.47s(5배 단축), 모바일 일관성 92%+ 확보; 모델과 DB의 역할 분업이 속도·정확도를 동시에 달성
기술 선택 근거
LoRA + 4-bit NF4 + 토큰 Pruning 조합
세 기법은 각각 다른 병목을 공략합니다. LoRA는 파라미터 수를 줄이고, NF4 양자화는 가중치 비트폭을 줄이며, 멀티링구얼 토큰 Pruning은 한국어에 불필요한 어휘를 제거해 메모리를 추가로 확보합니다. 어느 하나만 적용하면 목표인 3.0GB에 도달하지 못했고, 세 가지를 조합했을 때 76% 압축과 CPU 0.3s 추론을 동시에 달성했습니다.
전용 FAISS 벡터 DB로 콩글리쉬 지식 분리
630개 콩글리쉬 패턴을 파인튜닝으로 LLM에 주입하면 용례가 희소해 모델이 일관되게 기억하지 못합니다. RAG로 매번 검색하면 추론 지연이 늘어납니다. 전용 DB에 패턴을 저장하고 LLM은 문법·문맥 판단에만 집중하도록 역할을 분리하자 속도와 정확도 모두 올라갔습니다.
SQLite LRU 캐시 레이어 추가
FAISS 검색은 빠르지만 모바일 환경에서 동일 패턴이 반복 조회될 때 매번 벡터 연산을 실행하는 것은 낭비입니다. SQLite에 최근 조회 결과를 LRU 방식으로 캐싱하면 히트율 높은 패턴은 0.001s 이하로 처리됩니다. 이 레이어가 평균 응답 지연을 추가로 35% 단축했습니다.
실험 로그
E1Flan-T5면 충분할 수 있다
정답 교정은 가능하나 설명이 단조롭고 한국어·영어 혼합 표현에서 과보수적
→ 태스크 재정의 후 베이스 재검토
E2Qwen은 회화 자연화에 유리하다
대안 표현 다양성과 맥락 확장 우수
→ Qwen 채택, 단 경량화 연구가 따라붙는 결정
E3LoRA rank를 높이면 설명 품질이 오른다
rank 16에서 비용 대비 이득 최대, rank 8은 설명 다양성 감소
→ LoRA rank=16, alpha=32 채택
E44-bit NF4 양자화만으로 충분하다
모델 크기 급감, 일부 희귀 표현 설명 품질 저하
→ 일부 레이어 8bit 유지 + pruning으로 품질 손실 완화
E5병목은 모델 추론이다
cProfile 결과 FAISS 검색 0.21s, SQLite 조회 0.12s가 LLM 추론보다 컸다
→ FAISS IVF 재구성 + SQLite 인덱스 + LRU 캐시로 검색 병목 우선 해소
현장 이슈
양자화 강도를 높이면 교정문은 유지되어도 설명 문장의 문법 메타언어가 흔들렸다. 학습자 서비스에서 이 부분이 체감 품질을 크게 해쳤다. lm head와 일부 attention 경로를 보수적으로 유지했다.
RAG에서 너무 비슷한 예문만 주면 모델이 패턴을 복사해 사용자 문장을 과수정하는 현상이 있었다. 검색 다양성 제약을 추가했다.
개인화 메모리가 강하게 개입하면 이전 오류 유형이 현재 문장에도 과도하게 적용되는 메모리 오염 문제가 있었다. 세션 감쇠 규칙을 추가해 완화했다.
UiPath에서 Python을 직접 호출하는 방식은 라이브러리 경로·버전 차이로 잦은 실패를 일으켰다. FAISS HNSW → IVF 구조로 변경 후 유사 예문 검색 0.21s → 0.07s로 단축됐다.
배운 점

온디바이스 LLM 프로젝트에서 가장 큰 착각은 '모델이 병목'이라는 전제였다. cProfile로 실측해보니 FAISS 검색 0.21s, SQLite 조회 0.12s가 LLM 추론 시간보다 훨씬 컸다. 직관과 반대 방향으로 최적화를 시작했던 것이다. 두 번째 배움은 '지식'과 '언어 생성'의 책임 분리다. 630개 콩글리쉬 패턴을 파인튜닝으로 모델에 주입하면 희소 패턴은 필연적으로 망각된다. 모델이 언어·문맥 판단에만 집중하고 지식은 별도 벡터 DB가 관리하는 구조가, 두 책임을 하나의 모델에 합치는 것보다 훨씬 안정적이었다. 경량화는 단일 기법으로 목표에 도달하지 못했다. LoRA, NF4, 토큰 Pruning이 각각 다른 병목(파라미터 수, 비트폭, 어휘 크기)을 공략하기 때문에, 세 기법의 조합이 필요했다. '무엇이 병목인지 실제로 측정한 뒤 최적화하는 것'이 이 프로젝트 전체를 관통하는 교훈이었다.
